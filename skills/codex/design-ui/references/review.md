# 리뷰

실제 화면이 사용자의 과제·디자인 의도에 맞는지 평가한다. 리뷰 요청만 있으면 소스를 수정하지 않는다.

## 근거 확보

- 비교할 정본을 명확히 한다. 기존 제품과 맞는지 묻는다면 홈·관련 화면·토큰을 기준으로 삼는다. 구현 초안끼리 같다는 사실로 제품 정합성을 판정하지 않는다.
- 실제 화면을 열고 대상 섹션, 화면 폭, 데이터·상태를 구분해 캡처한다. 스크린샷을 직접 읽고, 원인 확인에 필요한 코드·측정만 추가로 본다. 캡처가 없으면 시각적 확인이 필요한 결론을 미확인으로 둔다.
- 외부 사례의 화면을 근거로 쓸 때도 원문·실제 화면을 확인한다. 같은 요소·상태의 전후인지 대조하고, 관련 표나 다른 지표를 요청한 그래프의 증거로 섞지 않는다. 접근 실패와 사례를 찾지 못한 결과를 구분한다.

## 판단할 것

- **과제와 위계:** 사용자가 다음 행동을 알 수 있는가. 코드·라벨·장식이 실제 핵심 혜택·가격·결론보다 강하게 보이지 않는가.
- **제품 정합성과 읽힘:** 제목·본문·숫자·보조 정보의 위계와 폰트가 기존 디자인에 맞는가. 크기 숫자뿐 아니라 실제 렌더와 정보의 우선순위를 본다.
- **행동과 상태:** 필요한 조건·예외·피드백이 보이고, 클릭 가능해 보이는 요소가 실제 동작하는가. 해당 과제에 필요한 상태를 [공통 화면 검증](../SKILL.md#공통-화면-검증)으로 확인한다.
- **화면 완성도:** 여백·정렬·밀도·잘림·대비·반응형이 읽기와 조작에 어떤 영향을 주는가. 장식의 유무 자체를 품질로 판정하지 않는다.

문제는 실제 관찰, 사용자에게 미치는 영향, 적용할 수정 방향으로 연결한다. 동작 결함·접근성 문제, 프로젝트 규칙과의 불일치, 선택 가능한 미적 취향을 구분한다. 영향이 크고 근거가 강한 발견부터 제시한다.

수치·자동 검사 통과는 그 검사의 범위를 확인한 것이다. 화면의 전체 품질이나 실제 사용자 성과를 입증한 것으로 표현하지 않는다. 모델의 의견도 주어진 질문과 근거 범위에 한정한다.

## 결과

발견과 근거 화면, 수정 우선순위, 확인한 범위와 미확인을 제시하고 끝낸다. 수정까지 요청받았다면 필요한 발견을 [개선](improve.md)으로 넘긴다.

[Taste의 리뷰·Look 절차](https://github.com/Leonxlnx/taste-skill/blob/12af471f627f866411b4bd785b19646d3672784c/skills/taste-skill/SKILL.md)를 실제 화면 비평의 참고로 삼았다. 특정 색·폰트·카드·그림자 금지 목록이나 모델 심사 점수를 의무 검사로 가져오지 않는다.
