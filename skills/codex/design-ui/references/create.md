# 생성

새 화면·페이지 또는 승인된 큰 방향 재설계에 사용한다. 국소 개선에는 이 절차 전체를 적용하지 않는다.

## 콘텐츠에서 방향 잡기

- 누가 어떤 상황에서 방문하고, 무엇을 이해·비교·실행해야 하는지 한 문장으로 잡는다. 정해지지 않은 제품 동작이 디자인을 막으면 그 선택만 구체화한다. 실제 요구 누락을 탐색해야 할 때만 설치된 `product-novelist`를 참고한다.
- 기존 제품이라면 홈·관련 화면·토큰·컴포넌트에서 유지할 디자인 체계와 동작을 찾는다. 사용자가 브랜드 변경을 요청하지 않았다면 그 체계 안에서 새 화면을 설계한다.
- 대상 고유의 사실, 실제 데이터, 이미지·제품 화면·로고 등 쓸 수 있는 에셋을 모은다. 없는 후기·고객 수·할인·성과·사진을 사실처럼 만들어 채우지 않는다. 프로토타입의 예시 데이터는 구분해 표시한다.
- 각 섹션이 답하는 사용자 질문, 전달할 주장, 이를 뒷받침할 콘텐츠를 짧게 짝짓는다. 관습적인 히어로·기능 카드·후기 순서를 먼저 채우기보다 이 관계로 필요한 섹션과 순서를 정한다.

## 필요한 만큼 방향 비교

방향이 열려 있으면 최대 3개의 의미 있게 다른 구성을 비교한다. 같은 콘텐츠·제약 안에서 정보 순서, 핵심 강조, 구성 방식이 어떻게 달라지는지와 추천 이유를 설명한다. 짧은 방향안이나 핵심 구간 시안부터 만들고, 모든 방향의 완성 페이지를 먼저 구현하지 않는다.

기존 디자인이나 사용자 선택으로 방향이 닫혀 있으면 그 방향으로 바로 진행한다. 시안 선택을 요청받았으면 비교 가능한 시안을 보여주는 데서 멈추고 선택을 기다린다. 구현까지 위임받은 가역적인 선택은 근거를 밝히고 진행한다. 미결인 브랜드·제품 의미를 임의로 확정하지 않는다.

고른 방향은 “이 화면의 고유한 내용이 어떤 구성·강조로 드러나는가”로 설명할 수 있어야 한다. 실제 콘텐츠가 안에 들어가지 않거나 없는 에셋을 전제하면 방향을 수정하고 이유를 남긴다.

## 구현과 검증

실제 스택·컴포넌트 안에서 데이터와 행동을 연결한다. 장식·모션은 정보 전달이나 상태 피드백에 필요한 만큼 쓰고 reduced-motion과 정적 표시를 고려한다. 고정 모션 개수나 특정 스타일을 강제하지 않는다.

선택한 시안과 실제 구현을 구분하고, 구현 요청은 [공통 화면 검증](../SKILL.md#공통-화면-검증)으로 닫는다. 시안만 요청받았다면 시안 범위와 아직 연결하지 않은 동작을 설명한다.
