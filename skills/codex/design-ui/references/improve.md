# 개선

기존 화면을 수정하고 검증하는 절차다. 기존 혜택 화면에서 사용한 디자인 정본 확인·섹션별 전후 비교·선택 누적·통합 검증을 일반화했다. 프로젝트별 콘텐츠와 개인 작업 기록은 포함하지 않는다.

## 수정 근거와 변경 전 상태

요청, 현재 화면, 기존 제품 규칙에서 바꿀 문제와 유지할 동작을 정한다. 리뷰 근거가 이미 충분하면 그대로 쓰고, 부족한 화면이나 정합성만 [리뷰](review.md)에서 확인한다. 전체 리뷰를 다시 의무 실행하지 않는다.

변경 전 화면과 주요 동작을 확인해 보존한다. 뒤늦게 만든 모형을 실제 변경 전 화면이라고 부르지 않는다. 현재 구현과 분리한 비교 시안은 시안으로 표시한다. 기존 작업자의 변경을 보존한다.

## 섹션별 전후 비교

1. 사용자 판단에 영향이 큰 섹션부터 다룬다. 화면 전체를 한꺼번에 바꿔 무엇이 좋아졌는지 알기 어렵게 만들지 않는다. 전반적 재설계가 요청된 경우에만 [생성](create.md)의 방향 설정을 사용한다.
2. 문제를 설명할 수 있는 수정안을 만들고 같은 요소·폭·배율·콘텐츠·데이터·상태의 전후를 보여준다. 한 비교는 어떤 선택을 판단하기 위한 것인지 분명히 한다. 연관된 폰트·간격·위계 수정은 한 안으로 묶을 수 있다.
3. 실제 화면이나 비교 이미지를 사용자에게 보여준다. 로컬 화면 캡처 경로를 나열하는 것만으로 비교를 대신하지 않는다. 차이와 추천 이유를 짧게 설명한다. 새로운 디자인 선택이 필요한 경우에만 사용자 선택을 받고, 이미 선택한 기준과 가역적인 구현 세부는 재승인 없이 적용한다.
4. 선택을 정보 우선순위와 디자인 규칙으로 해석해 다음 섹션에 이어간다. 사용자가 “할인율이 핵심”이라고 정했다면 코드나 보조 문구가 다시 시각적 우위를 차지하지 않는지 확인한다. 이 예시를 모든 화면의 정보 위계로 고정하지 않는다.

국소 수정은 바로 구현하고 확인한다. 여러 대안을 만들기 위한 대안, 새 인터뷰, 섹션마다 같은 승인 질문을 추가하지 않는다. 비평과 재수정 횟수는 [공통 화면 검증](../SKILL.md#공통-화면-검증)의 한도를 따른다.

## 합치고 다시 검증

선택한 안을 실제 구현에 합친 뒤 전체 흐름을 다시 연다. 섹션별로 괜찮았어도 이어 붙인 화면의 위계·반복·여백·상태 전환이 맞는지 확인한다. 모형에서 좋아 보였다는 사실만으로 실제 구현을 검증했다고 하지 않는다.

공통 화면 검증과 변경에 맞는 프로젝트 검사를 수행한다. 기존에 되던 계산·복사·조건 변경·탐색 등 관련 동작, 좁은 화면의 줄바꿈·높이·정렬을 확인한다. 확인한 화면 폭과 동작을 결과에 남기며, 모든 프로젝트에 같은 픽셀 값을 강제하지 않는다.

바꾼 내용, 선택·배제 이유, 전후 화면, 통합 후 검증 결과와 남은 문제를 전달한다. 다음 작업에 필요한 결정은 최종 응답 또는 기존 프로젝트 정본에 남긴다. 비공개 프리뷰와 공개 배포는 각각 실제 요청·권한 범위를 따른다.

[Taste의 기존 화면 개선 절차](https://github.com/Leonxlnx/taste-skill/blob/12af471f627f866411b4bd785b19646d3672784c/skills/taste-skill/SKILL.md)는 변경 전 기록, 스택·동작 유지, 같은 조건의 변경 후 확인에 참고했다. 해당 프로젝트에서 이 절차의 품질·시간·비용 효과는 실제 실행으로 따로 검증한다.
