# Design UI

화면을 쓰는 사람의 과제와 실제 콘텐츠에서 디자인을 판단한다. 먼저 요청한 결과와 수정 범위를 정하고, 아래에서 필요한 흐름만 읽는다.

| 요청한 결과 | 읽을 절차 | 끝내는 지점 |
|---|---|---|
| 새 화면·새 페이지·큰 방향 재설계 | [생성](references/create.md) | 요청한 시안 또는 구현과 그 검증 |
| 문제·정합성·사용성 평가 | [리뷰](references/review.md) | 화면 근거, 영향, 수정 우선순위. 소스 수정 없이 종료 |
| 기존 화면을 고치고 완성도 높이기 | [개선](references/improve.md) | 섹션별 비교, 수정, 통합 검증 |

“리뷰하고 고쳐줘”는 리뷰로 수정 근거를 잡고 개선으로 이어간다. 기존 화면의 국소 수정은 개선을 쓰고, 전체 방향을 바꾸는 요청에만 생성을 읽는다. 작은 변경에 새 방향·여러 시안·의무 인터뷰를 추가하지 않는다.

## 공통 판단과 실행

- 사용자 목적·승인된 선택 → 제공된 디자인 정본 → 기존 제품의 규칙과 동작 → 접근성·반응형 → 외부 참고 절차 순으로 판단한다. 비교 정본이 구현 초안인지 실제 제품의 디자인 체계인지 구분한다. 참고한 외부 절차의 색·폰트 금지나 모션 개수 같은 취향 규칙을 보편 기준으로 가져오지 않는다.
- 현재 화면, 코드, 토큰, 실제 콘텐츠·데이터와 사용 가능한 에셋을 먼저 확인한다. 외부 사례는 어떤 결정을 가져올지 설명하고 적용 조건을 확인한다. 필요한 디자인 지식은 프로젝트가 연결한 정본에서 해당 쟁점만 읽는다.
- 자료로 확인할 사실은 직접 찾고 가역적인 구현 선택은 승인 범위에서 진행한다. 사용자가 시안 선택을 요청했거나 남은 선택이 방향·의미를 바꿀 때만 권고안과 비교 근거를 제시해 선택받는다. 이미 고른 기준은 다음 섹션에도 적용한다.
- 브라우저는 사용자·프로젝트가 지정한 진입점을 따른다. Aside 환경이면 설치된 `aside-browser`의 안내를 먼저 읽는다. 접속·캡처 실패는 오류와 확인하지 못한 범위를 남긴다. 코드로 추론한 화면과 실제 관찰한 화면을 구분한다.
- 프로젝트의 스택·토큰·컴포넌트·실행 경로를 사용한다. 새 의존성이나 외부 도구는 실제로 필요한지 확인하고, 설치·게시·업로드·실거래는 기존 권한 범위를 따른다. 시안 검토가 배포 승인은 아니다.

색 전문 자료가 판단에 도움이 될 때만 “이 색상 쟁점은 전문 자료를 확인하면 도움이 됩니다. color-expert를 읽고 답변드릴까요?”처럼 이유와 함께 제안한다. 사용자가 동의하거나 이미 명시적으로 지정한 뒤에만 설치된 `color-expert`의 진입점과 필요한 자료를 읽는다. 자료를 먼저 읽고 사후 동의를 구하지 않는다. 일반 UI 작업·단순 색상 변경에는 이 질문을 자동으로 붙이지 않으며, 스킬이 없으면 설치를 전제하지 않는다.

## 공통 화면 검증

1. 실제 렌더를 열고 스크린샷도 직접 확인한다. 프로젝트가 지원하는 데스크톱·모바일 폭과 변경에 영향을 받는 좁은 폭을 고른다. 비교에는 같은 폭·배율·콘텐츠·데이터·상태를 쓴다.
2. 사용자 과제, 핵심 정보의 위계, 실제 로딩된 폰트·읽힘, 대비·포커스, 잘림·겹침·넘침을 본다. 변경한 흐름의 클릭·키보드·터치와 필요한 빈 상태·로딩·오류·열림·닫힘을 확인한다. 거래나 제출은 허용된 테스트 범위에서만 한다.
3. 구현을 완료하는 작업은 코드와 프로젝트에 맞는 검사로 동작을 확인한다. 배포 가능한 결과를 요청받았으면 가능할 때 최종 빌드도 로컬에서 확인한다. 시안 이미지·개발 서버만 확인한 경우 그 범위를 밝힌다.
4. 수정까지 요청받은 작업에서 미감 비평은 영향이 큰 문제 최대 3개를 골라 고친 뒤 다시 본다. 추가 비평은 새 근거가 있을 때만 이어가며 최대 3라운드로 끝낸다. 이 한도는 기능 오류를 남겨두는 완료 기준이 아니다. 해결되지 않은 기능·접근성 문제와 판단이 필요한 취향을 구분해 보고한다.

리뷰는 실제 관찰 범위와 발견을 제시하면 완료한다. 시안만 요청받았다면 시안을 직접 확인하고 구현하지 않은 동작을 밝힌다. 구현·개선은 요청한 결과가 있고 관련 화면·동작을 검증했을 때 완료한다. 확인하지 못한 항목은 미확인으로 남기며, 검증 결과나 사용자 효과를 추측해 채우지 않는다.

결과에는 무엇을 만들거나 고쳤는지, 선택·배제 이유, 실제 화면 또는 비교 자료, 검증 범위와 미결을 필요한 만큼 담는다. 결정은 최종 응답이나 프로젝트의 기존 디자인 정본에 남기며 별도 보고서를 의무로 만들지 않는다.
